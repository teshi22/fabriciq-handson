# 製造業データ：ロット調査の簡易サンプル

製品不良を起点に後続ロットを調査し、設備異常との関連も確認するための架空データです。図に合わせて、製品・製造工程・製造記録・製品不良・設備・設備異常の6種類で構成しています。既存の設備点検シナリオを置き換えず、比較用の試作として追加しています。

## このデータで答えたい問い

1. **製品Aの研削工程で寸法不良が発生した。そのロット以降に処理したロットを調査してほしい。**
2. **設備Aで主軸振動異常が発生した。この寸法不良と関係があるか？**

例の「不良C」に当たるのは、`DEF-001`の寸法不良です。ロットの前後を比較するために製造記録の開始・完了日時を、設備異常との関連を確認するために使用設備と異常の発生・復旧日時を持たせています。

## データ構成

業務データのCSVはすべてUTF-8、ヘッダーを除いて各5行です。ID・名称・関連付け・調査条件に加え、マスターには分類や型番、担当部署や標準時間、設備の種類や設置場所を持たせています。

| ファイル | 1行の意味 | カラム |
| --- | --- | --- |
| [processes.csv](./processes.csv) | 製造工程の種類 | `process_id`（工程ID・主キー）, `process_name`（工程名）, `department`（担当部署）, `standard_minutes`（1ロットの標準処理時間・分） |
| [products.csv](./products.csv) | 製品の種類 | `product_id`（製品ID・主キー）, `product_name`（製品名）, `product_category`（製品カテゴリ）, `model_code`（型番） |
| [equipment.csv](./equipment.csv) | 設備 | `equipment_id`（設備ID・主キー）, `equipment_name`（設備名）, `equipment_type`（設備種別）, `location`（設置場所） |
| [manufacturing_records.csv](./manufacturing_records.csv) | 製品ロットを、ある工程・設備で処理した記録 | `record_id`（記録ID・主キー）, `lot_id`（ロットID）, `product_id`（製品ID・外部キー）, `process_id`（工程ID・外部キー）, `equipment_id`（設備ID・外部キー）, `started_at`（処理開始日時）, `completed_at`（処理完了日時） |
| [defects.csv](./defects.csv) | 製造記録にひも付く不良の発生 | `defect_id`（不良ID・主キー）, `record_id`（記録ID・外部キー）, `defect_type`（不良内容）, `occurred_at`（不良発生日時） |
| [equipment_anomalies.csv](./equipment_anomalies.csv) | 設備異常の発生と復旧 | `anomaly_id`（異常ID・主キー）, `equipment_id`（設備ID・外部キー）, `anomaly_type`（異常内容）, `started_at`（異常発生日時）, `ended_at`（復旧日時） |

別途、質問と期待結果を5行にまとめた[investigation_qa.csv](./investigation_qa.csv)を用意しています。これはオントロジーに取り込むエンティティではなく、演習の確認用です。

質問と回答のペアだけを使う場合は、[qa.csv](./qa.csv)を使用してください。カラムは`question`と`answer`の2つで、難易度順に7組あります。1～3問目は関連データの参照・集計、4～5問目は日時条件を使う調査、6～7問目は設備異常との比較・複合調査です。これも演習の確認用であり、エンティティには取り込みません。

### データの前提

- ID・名称・不良内容は文字列、日時は日時型として扱います。CSVの日時はすべて日本時間（`+09:00`）です。
- マスターに追加した属性は文字列として扱い、`standard_minutes`だけは正の整数として扱います。標準時間は1ロットの当該工程での処理時間の目安であり、実績日時や設備異常の期間の代わりには使用しません。
- ロットは独立したエンティティにせず、`ManufacturingRecord`のプロパティとして持たせます。
- この5行では1ロットにつき研削工程の製造記録が1件あります。複数工程の履歴を追加する場合は、同じ`lot_id`に対して工程ごとに別の`record_id`を付けます。1つのロットは1種類の製品に属する前提です。
- 製品ごとの標準工程や工程順の定義は含めていません。今回扱うのは実際の工程処理の記録です。マスターには今回参照しない製品・工程・設備も含めています。
- 1製造記録に複数の不良をひも付けられます。不良発生日時は工程処理中の発生時刻が分かっている想定で、後日の検査による発見日時ではありません。
- 異常はすべて復旧済みとして、発生・復旧日時を記録しています。
- 既存データにも同名の[products.csv](../02_製造業データ/products.csv)や[equipment.csv](../02_製造業データ/equipment.csv)があるため、Fabricへ取り込む場合は別のレイクハウスを使うか、テーブル名を変えてください。

## オントロジーの構成

エンティティ型・リレーションシップ型・Mermaid全体図・設定順序は、[オントロジー設計](./ontology-design.md)を参照してください。

IDでつながっているだけでは、後続ロットや時間の重なりまでは判定できません。次の日時条件と合わせて探索します。「不良が設備異常によって発生した」という原因の関係は、あらかじめ登録していません。

## シナリオ1：不良発生ロット以降の調査

> 製品Aの研削工程で寸法不良（DEF-001）が発生した。そのロット以降に処理したロットを調査してほしい。

### 抽出ルール

1. `DEF-001`から`REC-002`をたどり、起点の製品・工程・ロット・処理開始日時を確認します。
2. 起点と**製品ID・工程IDが同じ**製造記録を取得します。設備IDは条件にしません。
3. **処理開始日時が起点の処理開始日時以上**の記録を抽出します。起点ロットも含め、サンプル内の最新までを対象にします。異常の復旧時刻で打ち切りません。
4. 重複しないロットIDを、処理開始日時順に返します。ロット番号の大小や、不良発生日時より後かどうかで並びを決めません。

| ロット | 製品 | 工程 | 設備 | 処理時間（2026-10-01・日本時間） | 判定 |
| --- | --- | --- | --- | --- | --- |
| `LOT-001` | 製品A | 研削 | 設備A | 08:00～09:00 | 起点より前のため除外 |
| `LOT-002` | 製品A | 研削 | 設備A | 09:00～10:00 | 起点。09:30に寸法不良が発生 |
| `LOT-003` | 製品A | 研削 | 設備A | 10:00～11:00 | 後続の調査候補 |
| `LOT-004` | 製品A | 研削 | 設備B | 11:00～12:00 | 別設備でも後続の条件を満たすため調査候補 |
| `LOT-005` | 製品B | 研削 | 設備A | 12:00～13:00 | 製品が異なるため除外 |

**回答：起点を含めてLOT-002・LOT-003・LOT-004の3ロット。** このうち追加の調査候補はLOT-003とLOT-004です。LOT-004には不良記録がありませんが、合格や安全が確認されたという意味ではありません。

不良の種類だけを指定して起点が複数見つかった場合は、勝手に1件を選ばず、不良IDや発生日時を確認します。この例は`DEF-001`を起点に固定しています。

## シナリオ2：設備異常と不良の関連調査

> 設備Aで主軸振動異常（ANOM-001）が発生した。寸法不良（DEF-001）と関係があるか？

### 判定ルール

1. `DEF-001` → `REC-002` → `EQ-001`とたどり、不良発生時に使っていた設備を確認します。
2. その設備にひも付く設備異常を取得します。
3. **設備IDが一致し、不良発生日時が異常期間内**なら、設備・時間の関連があると回答します。
4. 根拠として、ロット、使用設備、不良発生日時、異常内容、異常期間を返します。因果関係までは断定しません。

| 確認項目 | データ |
| --- | --- |
| 不良 | `DEF-001`：寸法不良 |
| ロット・製造記録 | `LOT-002`・`REC-002` |
| 使用設備 | `EQ-001`：設備A |
| 不良発生日時 | 2026-10-01 09:30 |
| 設備異常 | `ANOM-001`：主軸振動異常 |
| 異常期間 | 同日09:00以上11:00未満 |
| 結論 | 同じ設備で、異常期間中に不良が発生。関連を調べる根拠はあるが、原因とは断定できない |

比較用に、同じ設備でも時間帯が違う異常（`ANOM-002`、`ANOM-005`）と、同じ時間帯でも設備が違う異常（`ANOM-003`、`ANOM-004`）も入れています。どれも`DEF-001`との設備・時間の両方は一致しません。

### 異常期間中に処理したロットを調べる場合

こちらはシナリオ1とは別の条件です。製品や起点ロットを問わず、**設備IDが一致し、工程の処理時間帯と異常期間が重なる**記録を取得します。

```text
製造記録.started_at < 設備異常.ended_at
かつ
製造記録.completed_at > 設備異常.started_at
```

`ANOM-001`に該当するのはLOT-002・LOT-003です。LOT-001は異常発生の09:00に処理が完了しているため含みません。LOT-004は別設備、LOT-005は復旧後なので含みません。

### 時刻の境界と回答の注意点

- 処理時間帯・異常期間は、どちらも**開始時刻を含み、終了時刻を含まない**ものとします。復旧時刻ちょうどの不良は、その異常期間には含めません。
- 設備・時間の一致は関連調査の根拠であり、不良原因や影響範囲の確定ではありません。一致しない場合も、無関係や安全を証明するものではありません。
- 「後続ロットの候補」と「設備異常の期間に処理したロット」は別の集合です。回答では、適用した条件と根拠を明示します。
- 期待結果5件は[investigation_qa.csv](./investigation_qa.csv)にまとめています。
